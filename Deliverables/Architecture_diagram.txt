3. DATA AND FILE STORAGE
------------------------

  +----------------------------------------------------+     +------------------+
  | Relational database                                |     | Uploaded photos  |
  |                                                    |     |                  |
  | SQLite: default for local development/tests       |     | Backend file     |
  | PostgreSQL: configured with DATABASE_URL in       |     | system / mounted |
  | deployment                                         |     | persistent disk  |
  |                                                    |     |                  |
  | users                 categories                  |     | image_url refers |
  | items                 wishlists                   |     | to served file   |
  | user_preferences      swap_proposals              |     +------------------+
  | swap_messages         swap_history
  | trust_logs            notifications
  +----------------------------------------------------+

  Main relationships
  - A user owns many items and wishlist entries.
  - An item belongs to an owner and may belong to a category.
  - A wishlist entry joins a user to a wanted item.
  - A swap proposal joins a giver, receiver, item, and cycle.
  - Messages and notifications are associated with a swap cycle.
  - Trust logs, preferences, and swap history refer to users.

  The SQL setup script creates the PostgreSQL schema. The application also
  calls SQLAlchemy create_all() at startup to create missing tables; this does
  not alter existing tables, so deployed schema changes need migrations.

4. SWAP MATCHING AND LIFECYCLE
------------------------------

  Wishlist entries + available items
                 |
                 v
  Build directed graph: a user points to the owner of an item they want
                 |
                 v
  Tarjan SCC cycle detection
                 |
                 v
  Filter: cycle has at least two users; respect available-item and
          user-avoidance constraints
                 |
                 v
  Proposals created for cycle transfers; notifications sent
                 |
                 v
  Participants respond to their proposals
         |                       |
         | all accepted          | rejection / expiry / cancellation
         v                       v
  Complete cycle; update      Release pending items, update proposal
  item ownership/status,      statuses, trust data as applicable, and
  trust logs and history     notify affected users
         |
         v
  Accepted participants can use cycle chat; messages create notifications

  Proposal expiry is checked by the FastAPI background loop and can also be
  processed through the swap expiration endpoint. Notifications are refreshed
  by the browser through the notifications REST endpoints (10-second polling).

5. AUTHENTICATION AND TRUST
---------------------------

  Register/login
      -> FastAPI verifies credentials and returns JWT
      -> Frontend stores session token and sends it as a bearer token
      -> Authenticated endpoints enforce user ownership and admin role

  Swap outcomes update trust score/rejection information and write trust_logs.
  Users can inspect their score/history; administrators can disable accounts.

6. TESTING, CI, AND DEPLOYMENT
------------------------------

  Developer change
      |
      v
  GitHub Actions on push / pull request
      |
      +--> Backend: pytest + coverage, Ruff lint and format checks
      |
      +--> Frontend: Vitest + coverage, Oxlint, TypeScript/Vite build,
      |    production dependency audit
      |
      +--> Playwright: mocked API E2E + real backend integration E2E
           (temporary SQLite database)
      |
      +--> Only after passing checks, push to main:
           trigger Render backend deployment and wait for /health
           to report the expected commit

  Deployed services
  - Frontend: React application hosted on Vercel
  - Backend: FastAPI hosted on Render
  - Database: PostgreSQL hosted on Render
  - Uploaded files: backend filesystem; persistent disk is required to retain
    uploads across service restarts/redeployments
  - User guide: separately published to GitHub Pages

  Local development uses SQLite by default. DATABASE_URL selects PostgreSQL
  for deployment. Uploaded image files are separate from the relational schema.

7. END-TO-END USER JOURNEY
--------------------------

  1. A family registers, signs in, and adds items (optionally with photos).
  2. The family browses available items and adds wanted items to a wishlist.
  3. The backend builds the wishlist/ownership graph and searches for cycles.
  4. The user proposes a compatible cycle; participants receive notifications.
  5. Participants accept or reject their proposals; accepted cycles can chat.
  6. When all proposals are accepted, the backend records the completed swap,
     updates item state and trust data, and makes the swap visible in history.
  7. Expiration processing handles proposals that remain unresolved.
